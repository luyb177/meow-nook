# 错误码设计规范

## 一、设计目标

为了统一系统异常处理机制，规范前后端交互中的错误返回格式，提高系统可维护性、可排查性以及团队协作效率，项目采用统一的业务错误码体系。

错误码具备以下目标：

* 统一错误返回结构
* 快速定位错误来源
* 明确区分系统错误与业务错误
* 支持日志追踪与监控告警
* 支持前端精细化提示处理
* 支持微服务之间统一错误传递

---

## 二、错误码格式设计

采用固定长度 **6位数字错误码**：

```text
AA BB CC
```

即：

```text
前2位 + 中2位 + 后2位
```

含义如下：

| 字段 | 位数 | 含义              |
|----|---:|-----------------|
| AA | 2位 | 错误大类（系统级 / 业务级） |
| BB | 2位 | 子模块 / 功能分类      |
| CC | 2位 | 具体错误编号          |

例如：

```text
200101
```

表示：

* `20`：用户模块
* `01`：注册 / 用户基础信息
* `01`：用户不存在

---

## 三、错误码分层说明

---

# 1. AA：错误大类（一级分类）

## 系统级错误（10 ~ 19）

系统级错误主要用于基础设施、依赖服务、服务内部异常等非业务逻辑错误。

| 编号 | 模块          | 说明                        |
|----|-------------|---------------------------|
| 10 | 通用系统错误      | 未分类系统异常                   |
| 11 | 数据库错误       | MySQL / PostgreSQL 等数据库异常 |
| 12 | Redis错误     | Redis连接、缓存异常              |
| 13 | MQ消息错误      | Kafka / RabbitMQ 消息异常     |
| 14 | RPC调用错误     | gRPC / HTTP 服务调用异常        |
| 15 | 第三方服务错误     | 短信、邮箱、支付等外部服务             |
| 16 | 文件存储错误（OSS） | 图片上传、文件存储异常               |
| 17 | 配置错误        | 配置缺失、环境变量异常               |
| 18 | 权限认证错误      | Token、JWT、登录鉴权异常          |
| 19 | 限流熔断错误      | Sentinel、限流、降级、熔断         |

---

## 业务级错误（20 ~ 99）

业务级错误用于具体业务流程中的异常处理。

| 编号 | 模块    | 说明         |
|----|-------|------------|
| 20 | 用户模块  | 注册、登录、用户信息 |
| 21 | 猫咪模块  | 猫咪档案、领养猫信息 |
| 22 | 任务模块  | 志愿任务、任务认领  |
| 23 | 领养模块  | 领养申请、审核流程  |
| 24 | 动态模块  | 社区动态、帖子内容  |
| 25 | 评论模块  | 评论、回复、点赞   |
| 26 | 积分模块  | 积分获取、积分消费  |
| 27 | 管理员模块 | 后台管理权限     |
| 28 | 审核模块  | 内容审核、审批流   |
| 29 | 通知模块  | 消息通知、系统提醒  |

---

# 2. BB：子模块（二级分类）

用于进一步细分业务功能。

以用户模块（20）为例：

| 编号 | 子模块  |
|----|------|
| 01 | 注册   |
| 02 | 登录   |
| 03 | 用户资料 |
| 04 | 权限管理 |
| 05 | 积分相关 |
| 06 | 邮箱验证 |
| 07 | 密码找回 |

例如：

```text
200101
```

表示：

```text
20 用户模块
01 注册功能
01 用户已存在
```

---

# 3. CC：具体错误编号（三级分类）

用于具体错误场景。

例如：

| 编号 | 错误    |
| -- | ----- |
| 01 | 不存在   |
| 02 | 已存在   |
| 03 | 参数错误  |
| 04 | 状态异常  |
| 05 | 权限不足  |
| 06 | 重复操作  |
| 07 | 数据冲突  |
| 08 | 操作失败  |
| 09 | 超出限制  |
| 10 | 服务不可用 |

例如：

```text
220102
```

表示：

```text
22 任务模块
01 创建任务
02 任务已被认领
```

## 六、错误返回结构规范

统一返回结构：

```json
{
  "code": 200101,
  "msg": "用户不存在",
  "data": {}
}
```

说明：

| 字段   | 类型     | 说明                  |
| ---- | ------ | ------------------- |
| code | int    | 业务错误码               |
| msg  | string | 用户可见提示信息            |
| data | any    | 成功时返回数据，失败时通常为 null |

---

## 七、设计原则

### 1. 错误码唯一

全系统内错误码必须唯一，不允许重复定义。

---

### 2. 错误信息稳定

错误码一旦发布，不允许随意修改语义。

---

### 3. 前端依赖 code，不依赖 msg

前端逻辑判断必须基于 `code`，不能基于 `msg`。

---

### 4. 系统错误不暴露内部细节

例如：

```text
数据库连接失败
```

而不是：

```text
dial tcp 10.0.0.1:3306 connection refused
```

内部详细错误仅记录日志。

---

### 5. 使用 Wrap 保留底层错误

例如：

```go
return errorx.WrapDatabase("查询用户失败", err)
```

便于日志排查与链路追踪。
